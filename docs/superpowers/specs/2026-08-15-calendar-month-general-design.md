# 大六壬历法与月将阶段设计

日期：2026-08-15  
状态：用户已确认

## 1. 目标

实现大六壬规则链的第一个真实计算阶段：将起课输入转换为可追溯、可人工修正、可供下游消费的“历法与月将”快照。

本阶段必须解决：

- 北京时间输入与 23:00 子初换日。
- 农历日期、年柱、月柱、日柱、时柱。
- 当前节、中气、月建、月将和占时。
- 自动值与人工有效值的并存、恢复和来源标记。
- 规则证据、边界时刻和开发期交叉核验。
- 桌面与移动端的历表矩阵审核界面。

本阶段不实现天地盘、四课、三传、天将、大六壬课式计算或三维模型，也不调用第三方库的一体化大六壬结果。

## 2. 已确认规则口径

### 2.1 时间基准与支持范围

- 输入时间固定按北京时间 UTC+8 解释。`Asia/Shanghai` 是领域标签，不应用历史夏令时偏移。
- 输入与审核界面支持秒级时间；原有只含分钟的输入按 `:00` 秒解释。
- 经度和纬度保留在起课上下文中，本阶段不换算地方时或真太阳时。
- 自动历法计算支持 1900-01-01 至 2100-12-31。
- 范围外保留输入并返回结构化错误，不生成历法快照；用户不能用不完整人工值绕过该边界进入天地盘。

### 2.2 民用日期与干支日界

- 农历日期按北京时间民用日期在 00:00 更换。
- 日柱在子初 23:00 换日。23:00–23:59 使用下一民用日的干支日。
- 审核界面同时展示“民用日期”和“生效干支日期”。
- 23:00–00:59 均属于子时；时干使用换日后的有效日干推导。

### 2.3 年柱与月柱

- 年柱在立春的精确时刻换年。
- 月柱在十二“节”的精确时刻换月：立春起寅月，之后依次轮转。
- 输入时刻恰好等于交接时刻时，采用交接后的新年柱或新月柱。
- 年干推月干、日干推时干采用独立、版本化的传统规则函数，不依赖第三方库的隐式门派默认值。

### 2.4 月将

月将在十二“中气”的精确时刻交接。输入时刻恰好等于交接时刻时，采用新月将。

| 中气 | 月将地支 | 月将名称 |
| --- | --- | --- |
| 雨水 | 亥 | 登明 |
| 春分 | 戌 | 河魁 |
| 谷雨 | 酉 | 从魁 |
| 小满 | 申 | 传送 |
| 夏至 | 未 | 小吉 |
| 大暑 | 午 | 胜光 |
| 处暑 | 巳 | 太乙 |
| 秋分 | 辰 | 天罡 |
| 霜降 | 卯 | 太冲 |
| 小雪 | 寅 | 功曹 |
| 冬至 | 丑 | 大吉 |
| 大寒 | 子 | 神后 |

每个月将的有效区间为 `[本中气精确时刻, 下一中气精确时刻)`。

### 2.5 占时

- 自动占时取北京时间所在双时辰的地支。
- 不使用地点或真太阳时修正。
- 人工占时覆盖后仍保留自动占时，并标记有效值来源为人工。

## 3. 技术路径

### 3.1 采用方案

采用“领域适配层 + 成熟历法库”的方案：

- 使用 `lunar-typescript` 的锁定版本提供公历转农历、节气时刻和干支循环所需的历法原始能力。
- 第三方库封装在 `CalendarAdapter` 后，不允许视图、快照或后续大六壬模块直接调用。
- 本项目的 `CalendarPolicy` 负责北京时间、23:00 日界、立春换年、按节换月、按中气换月将和双时辰等已确认规则。
- 不使用第三方库直接给出的一体化大六壬结果。
- 生产运行完全离线。在线或独立天文数据源只用于开发期交叉核验，不进入运行依赖。

候选交叉核验来源包括 Astronomy Engine、JPL Horizons 和公开权威历表。交叉核验材料记录在测试案例的来源说明中，不在运行时请求网络。

### 3.2 分层职责

`CalendarAdapter`

- 接收北京时间对应的明确年月日时分秒。
- 返回农历日期、相邻节气精确时刻及计算干支所需的原始历法数据。
- 对范围首尾的输入允许读取相邻年份的节气数据，但可提交的起课时间仍严格限制在 1900–2100。
- 不判断大六壬月将，不应用 23:00 换日，不应用人工修正。

`CalendarPolicy`

- 应用本规格第 2 节的全部规则。
- 生成自动四柱、月建、月将、占时和边界证据。
- 每个纯函数只负责一个规则，使用稳定规则编号。

`CalendarCorrections`

- 将四柱、月将、占时的人工修正叠加到自动结果之上。
- 自动值不可被删除或改写。
- 每个字段产生独立的有效值与来源。

`CalendarSnapshotComposer`

- 只有在自动结果和修正结果均完整有效时才创建 `calendar` 快照。
- 快照 `stage` 固定为 `calendar`，`dependsOn` 固定为空数组。
- 全部字段自动计算时，快照级 `source` 为 `automatic`；任一字段采用人工值时为 `manual`。逐字段 `source` 仍是审核与展示的权威来源。
- 输入或修正变化后，通过现有依赖图使受 `calendar` 影响的下游快照失效。

## 4. 数据模型

### 4.1 审核值

每个可修正字段使用统一结构：

```ts
interface ReviewedValue<T> {
  automatic: T;
  effective: T;
  source: "automatic" | "manual";
}
```

恢复自动值时，`effective` 回到 `automatic`，`source` 回到 `automatic`。

### 4.2 历法结果

```ts
interface CalendarResult {
  civilDateTime: string;
  effectiveGanzhiDate: string;
  lunarDate: {
    year: number;
    month: number;
    day: number;
    isLeapMonth: boolean;
    display: string;
  };
  pillars: {
    year: ReviewedValue<string>;
    month: ReviewedValue<string>;
    day: ReviewedValue<string>;
    hour: ReviewedValue<string>;
  };
  monthBuild: EarthlyBranch;
  monthGeneral: ReviewedValue<{
    name: MonthGeneralName;
    branch: EarthlyBranch;
  }>;
  divinationHour: ReviewedValue<EarthlyBranch>;
  boundaries: {
    previousJie: SolarTermBoundary;
    nextJie: SolarTermBoundary;
    previousZhongQi: SolarTermBoundary;
    nextZhongQi: SolarTermBoundary;
  };
  evidence: readonly CalendarEvidenceStep[];
}
```

`SolarTermBoundary` 包含节气名称、北京时间精确时刻、节或中气类别及是否已经生效。`CalendarEvidenceStep` 包含规则编号、输入摘要、结论和受影响字段。

### 4.3 规则编号

首版至少包含：

- `calendar/beijing-time-v1`
- `calendar/zi-initial-rollover-v1`
- `calendar/year-at-li-chun-v1`
- `calendar/month-at-jie-v1`
- `calendar/day-cycle-v1`
- `calendar/hour-double-hour-v1`
- `calendar/hour-stem-v1`
- `calendar/month-general-at-zhongqi-v1`
- `calendar/manual-correction-v1`

规则语义变化时新增版本，不静默改变历史快照的含义。

## 5. 计算流程

1. 验证输入时间、地点、坐标和人工修正格式。
2. 将带秒的 `datetime-local` 字符串按固定 UTC+8 解释，不交给浏览器本地时区或历史夏令时规则隐式转换；缺省秒补为 `00`。
3. 校验年份是否在 1900–2100。
4. 通过适配器取得农历日期、节气边界和基础历法数据。
5. 根据输入时刻计算民用日期与生效干支日期。
6. 按立春、十二节、六十日循环和双时辰规则生成自动四柱。
7. 按当前节确定月建，按当前中气确定月将。
8. 生成自动占时。
9. 应用逐字段人工修正并保留自动值。
10. 验证结果完整性，生成证据步骤与不可变 `calendar` 快照。
11. 快照交给审核界面；天地盘阶段只读取完整有效快照。

## 6. 审核界面：历表矩阵

采用用户确认的 B“历表矩阵审核台”。

### 6.1 桌面布局

- 顶部显示“规则阶段 01 / 06”、阶段名称、北京时间规则和计算状态。
- 时间带并列展示民用时间、23:00 换日规则和生效干支日期。
- 主区使用八格矩阵：年柱、月柱、日柱、时柱、农历日期、月建、月将、占时。
- 每格展示自动值、有效值和自动/人工来源徽标。
- 点击格子后，右侧证据栏显示该字段的规则步骤、规则编号、交接时刻与结果。
- 可修正字段在证据栏中提供单项修正和恢复自动值。
- 下方显示前后相邻的节与中气精确时刻。

### 6.2 移动端

- 八格矩阵改为两列，不缩小为难读的小字。
- 点击格子后，证据和人工修正从底部抽屉展开。
- 所有控件保持至少 44 像素触控高度和可见键盘焦点。

### 6.3 视觉规则

- 延续现有冷调宋式 × 青铜色板和字体系统。
- 人工有效值使用旧金色边框与文字，自动值仍在同一格中保留。
- 不使用无意义的批准按钮、状态弹窗或形式化审批流。
- 阶段状态只表达“等待计算、可审核、计算失败、已形成快照”。

## 7. 错误与降级

错误返回稳定代码和面向用户的中文说明：

- `OUT_OF_SUPPORTED_RANGE`：超出 1900–2100。
- `INVALID_BEIJING_DATETIME`：北京时间输入无效。
- `CALENDAR_ADAPTER_FAILURE`：历法适配器没有返回完整数据。
- `SOLAR_TERM_BOUNDARY_FAILURE`：无法取得完整节气边界。
- `INVALID_CALENDAR_CORRECTION`：人工修正格式或干支组合无效。
- `CALENDAR_RESULT_INCOMPLETE`：自动值或有效值不完整。
- `CROSS_CHECK_DISCREPANCY`：开发期交叉核验差异超过 60 秒，或差异改变边界归属。

错误不得生成部分历法快照，不得猜测后续值。在线交叉核验服务不可用只影响开发校验，不影响产品离线运行。

## 8. 标准案例与审核门槛

正式计算代码前先建立来源可追溯的案例证据表。每个案例记录北京时间、数据来源、独立交叉核验值、预期结果和规则编号。

### 8.1 普通案例

选择一个远离 23:00、节和中气边界的 1900–2100 日期，完整核对农历、四柱、月建、月将和占时。

### 8.2 子初换日案例组

对同一民用日的 22:59、23:00、23:01 分别核对：

- 民用日期不变。
- 23:00 起生效干支日期和日柱进入次日。
- 三个时刻均按所属双时辰产生正确占时和时柱。

### 8.3 节气边界案例组

- 立春精确时刻前、恰好相等、之后：核对年柱和月柱。
- 一个非立春“节”的精确时刻前后：核对月柱。
- 一个“中气”的精确时刻前、恰好相等、之后：核对月将。

这些案例的预期值在进入正式实现前提交给用户审核；用户确认后固化为回归测试，不增加产品内审批流程。

## 9. 测试与完成标准

### 9.1 领域测试

- 北京时间解析不受运行机器时区影响。
- 22:59、23:00、23:01 日界行为。
- 立春、十二节和十二中气在前一秒、精确时刻、后一秒的归属。
- 年干推月干、六十日循环、日干推时干和十二双时辰。
- 十二中气到月将名称与地支的完整映射。

### 9.2 适配器与交叉核验测试

- 适配器只返回原始历法数据，不应用大六壬月将或人工修正规则。
- 标准案例与锁定的交叉核验数据一致。
- 差异超过 60 秒或改变边界归属时测试失败。

### 9.3 修正与快照测试

- 自动值始终保留。
- 四柱、月将和占时可分别修正与恢复。
- 非法修正不替换旧有效值。
- 快照阶段、依赖、规则编号和字段来源完整。
- 输入或修正变化后，现有依赖图正确移除受影响下游快照。

### 9.4 界面与浏览器测试

- 八格矩阵和证据详情显示真实快照，不包含演示硬编码结果。
- 自动值、有效值和来源对辅助技术可识别。
- 字段错误与控件正确关联。
- 桌面和移动端无横向溢出。
- 全部可见控件可通过键盘到达，焦点可见。
- 移动端证据抽屉可打开、关闭并恢复焦点。

### 9.5 完成定义

- 用户确认的标准案例全部通过。
- 单元测试、生产构建和浏览器测试通过。
- `calendar` 快照能够稳定生成、验证、人工修正和失效传播。
- 应用可在历表矩阵中展示完整证据，但仍不生成天地盘或伪造课式。
